Project Contract: build prompt

Vendor-linked project contracts in Vue, about half the same as the RentOut sale agreement. Copy the prompt and paste it into a new session.

Goal

Build a new Project Contract module. A project contract is made with a vendor (an accounts row where model = 'Vendor', see Account::scopeVendor()). The domain is about 50% the same as the RentOut sale agreement (App\Models\RentOut with agreement_type = sale), so reuse its ideas. Do not reuse its UI. This module is built entirely in Vue 3, not Livewire.

Step 0 (do this first): before writing any app code, build a static preview at docs/project-contract-preview.html with plain HTML, Bootstrap-theme styling and FA 4.3 icons. It must show (1) the Create Contract form, (2) the contract view with its tabs, and (3) the Add Payment Term modal. Stop there and let me review it. After I approve, implement the steps below.

2. Payment terms: flexible, not generated

This is the main difference from rentals. RentOut creates a fixed schedule from rent × frequency (see MultiplePaymentTermModal). Project contracts do not work that way. The user adds one term at a time, whenever the project plan calls for it, and each term can have any amount and due date.

  • Table project_contract_payment_terms: project_contract_id, label (e.g. "Mobilisation 20%"), due_date, amount, paid, balance, status (pending / partial / paid), remarks, created_by, tenant and branch columns. Model it on RentOutPaymentTerm.
  • Add, edit and delete one term at a time. Editing or deleting a term that has payments is blocked.
  • Show a plan meter on the Terms tab: "3 of 6 terms scheduled · QAR 45,000 of 120,000 allocated · 75,000 unallocated".
  • If the scheduled term total would go above the contract amount, show a warning and require an extension (section 4) to increase the amount. Do not silently allow it.
  • If the number of terms goes above no_of_terms, show a soft warning only.

3. Payments and transactions

  • Pay one term, or several selected terms (same idea as PaySelectedModal). Fields: date, amount (part payment allowed), payment method, cheque no./date/bank for cheques, remark.
  • Table project_contract_transactions, modelled on RentOutTransaction: date, debit/credit, account_id, source/source_id, model/model_id (the term), journal_id, journal_entry_id, payment_type, cheque fields, voucher_no, remark, created_by.
  • Accounting: every payment posts a balanced journal through App\Actions\Journal\CreateAction. Use Dr Vendor / Cr Payment Method, because we are paying the vendor. Deleting a payment reverses its journal and restores the term's paid and balance. Follow the accounting-journals skill.
  • Transactions tab: a ledger list with a running balance plus totals for Contract · Paid · Outstanding.

4. Contract extensions

  • Table project_contract_extends, modelled on RentOutExtend: old_end_date, new_end_date, additional_amount (can be 0), additional_terms (can be 0), reason, optional document, created_by.
  • An extension updates the header's end_date, contract_amount and no_of_terms in one DB transaction. The original values stay in the extension history.
  • The Extensions tab shows a timeline of every extension.

5. Documents and notes

  • project_contract_documents (modelled on RentOutDocument): document type, name, file path, uploaded_by. Multi-file drag-drop upload; reuse the idea in components/Ticket/FileDrop.vue. Preview images and PDFs, plus download and delete.
  • project_contract_notes (modelled on RentOutNote): note text, created_by, timestamps. Shown as a feed, newest first, with edit and delete for the author.

6. Security deposit

Model it on RentOutSecurity and App\Actions\RentOut\Security\SyncAccountingAction. Use the same approach: on every save, reverse the existing journals and post them again, inside a DB transaction, so running it twice gives the same result.

  • Table project_contract_securities: direction (received from vendor, the default / paid to vendor), form (bank guarantee / cash / cheque), purpose (performance bond, advance payment guarantee, retention security, general), amount, account_id (payment method, cash only), bank_name, reference_no (guarantee or cheque no.), valid_from, valid_until, cheque_date, received_date, status (held / returned / forfeited, plus partial returns), settled_date, settled_amount, reason, document path, renewed_from_id (a renewal links to the guarantee it replaces), created_by.
  • Accounting depends on the form:
    • Cash received from the vendor → Dr Payment method / Cr Vendor Security Deposit (a new locked liability account, slug vendor_security_deposit, added in AccountSeeder and a migration for every tenant).
    • Returned → Dr Vendor Security Deposit / Cr Payment method.
    • Forfeited → Dr Vendor Security Deposit / Cr Forfeited Deposits (income).
    • Cash paid to the vendor goes through an asset account instead (security_deposit_paid).
    • Bank guarantees and undeposited cheques are tracked only, with no journal, until they are encashed.
  • Security tab: totals for Required / Held / Returned / Forfeited, filters for All / Held / Returned or forfeited, and one card per security showing its validity as a bar. Actions: Return, Forfeit or Encash, and Record renewal for guarantees.
  • Expiry alerts: warn when a guarantee expires before the contract end date, or within 30 days. Show this on the card, in the details panel and in a daily notification.
  • Return and forfeit can be partial. Forfeit needs a reason. Both go through approval when the "Returning or forfeiting security" approval toggle is on.
  • A contract cannot be marked Completed while any security is still Held.

7. Vendors (list, create, edit, delete)

Vendors already exist as accounts rows with model = 'Vendor'. There is an existing Livewire page at App\Livewire\Account\Vendor\Page/Table (route account::vendor::index) that only edits name, mobile, email, place and credit period. Do not create a new table. Build the Vue vendor screens inside this module on top of the same accounts rows, and write through the existing App\Actions\Account\CreateAction / UpdateAction / DeleteAction with model = 'Vendor'. Every field below is already a column on accounts, the same ones the customer KYC form uses.

  • Vendor form, with the same sections as the customer form and icon-prefixed inputs, compact: three fields per row on wide screens (two on tablets, one on phones), small labels and inputs, slim section headers, and one-line textareas that grow as you type. The vendor list uses dense rows too.
    • Basic Information: Name* (name), Name (Arabic) (alias_name, RTL), Vendor Type (Company / Individual / Subcontractor / Supplier, a new small enum or config list), Date Of Birth (dob), Credit Period (days) (credit_period_days), Tax / CR No. (cr_number / tax_no).
    • Contact Information: Mobile* (mobile), WhatsApp (whatsapp_mobile), Emergency Contact No (emergency_contact_no), Email (email), P.O. Box (po_box), Contact Person (contact_person).
    • Personal Details: ID Number (id_no), ID Expiry Date (id_expiry_date), Passport No (passport_no), Occupation (occupation), Nationality (nationality, searchable), Company (company), Marital Status (marital_status), Residential Address (residential_address).
    • Employment / Business Details: Position / Nature Of Business (position_nature_of_business), Monthly Income (monthly_income), Employer / Business Address (employer_address).
    Validate with a Form Request: name required (max 100), mobile required (max 15), email format, and a unique name per tenant among vendors.
  • Vendor list: search (name, Arabic name, mobile, CR no.), Vendor Type filter buttons, and columns Vendor (initials badge + Arabic name), Type, Mobile, Email, CR / Tax No., Contracts, Committed and Balance (from the ledger, not a stored column). Edit and Delete on each row, plus export.
  • Delete: blocked when the vendor has contracts or journal entries. Show "Can't delete vendor: it has N contracts and ledger entries" instead of a delete button. Otherwise confirm before deleting.
  • Create from the contract form: a + New button beside the Vendor select opens a quick-create modal using the same VendorForm component. Basic and Contact are shown; Personal and Employment sit under a "More details" section that opens on click. "Save and select" creates the vendor, adds it to the Vendor select, selects it, and shows "Vendor created and selected".
  • Permissions: reuse the existing vendor.view|create|edit|delete.

8. Admin approval levels

  • Levels (no settings screen). Level 1 is the Project Manager role and always applies. Level 2 is the Admin role when the amount is above QAR 50,000. Keep them in one place, a per-tenant Configuration JSON seeded with these defaults, so they can change later without code changes. Do not build a screen for them.
  • What needs approval: new contracts, extensions, edits to the vendor, dates or amount of an active contract, and returning or forfeiting security.
  • Polymorphic table project_contract_approvals: approvable_type/approvable_id (the contract or an extension), level, approver_role, status (pending / approved / rejected), acted_by, acted_at, comment. On submit, create one row per level that applies, using the levels and amount at that moment.
  • Flow: Save as draft, or Submit for approval. Each level is approved in order. When the last level approves, the contract becomes Active, or the extension's changes are applied. A rejection must have a comment and sends the contract back to Draft. Resubmitting starts again at level 1.
  • Rules that always apply: nobody can approve their own submission, each level must be a different person, and one approval per level is enough. Notify the approvers when something reaches their level. Terms, payments and extensions are locked until the contract is Active.
  • UI: a banner on the view ("Waiting for your approval · Level 2 · Admin") with Approve and Reject buttons, shown only to whoever can act. An approval timeline in the details panel. An Approve/Reject modal that requires a comment when rejecting. A "Pending approval" filter on the list.
  • Permission project contract.approve, plus matching on the approver's role or user for the current level.

10. Architecture: follow the Ticket console pattern

  • Vue mount: copy the resources/js/ticket-console.js approach. Add an entry file such as resources/js/project-contract.js that uses mountVueApp(...) from utils/createVueApp.js, and register it in vite.config.js. Components go in resources/js/components/ProjectContract/, with an api.js like components/Ticket/api.js.
  • Blade host pages (like resources/views/ticket/index.blade.php) render only the mount div, initial props and @vite.
  • Backend: a controller that returns JSON, like TicketController, with Form Requests for every write. All write logic goes in app/Actions/ProjectContract/ (Create, Update, Delete, PaymentTerm/*, Payment/*, Extend, Document/*, Note/*). Follow the action-layer skill.
  • Routes: put them in their own route file with project-contract:: name prefixes and ->can() on every route.
  • Permissions: add to config/permissions.php and the seeder: project contract.view|create|edit|delete|payment|extend|security|document|note|approve|report. Add a sidebar entry behind @can.
  • Styling: Bootstrap theme classes only, theme variables, light and dark mode. Use an eye-friendly palette (copy the tokens from the preview): a calm blue accent, warm off-white backgrounds instead of pure white, soft dark-grey text instead of black, muted green/red/amber for statuses, and low-saturation dashboard gradients. Use Font Awesome 4.3 icons only. Use toastr for success and error messages and SweetAlert for delete confirmations.

11. Tests

Write Pest feature tests for: creating the contract with validation (vendor must be a Vendor account), adding a term and blocking it when it goes over the contract amount, partial and full payments that update term status and post balanced journals, payment deletion that reverses its journal, an extension that updates the header and keeps history, security deposits (cash posts and reverses balanced journals, guarantees post nothing, partial return, forfeit to income, Completed blocked while security is held), vendor CRUD (create with every detail field, the Arabic name kept, delete blocked when contracts or ledger entries exist, quick-create from the contract form selects the new vendor), the approval chain (levels chosen by amount, applied in order, self-approval blocked, rejection returns the contract to Draft, terms locked until Active), tenant isolation, and permission 403s. Run only those tests with php artisan test --compact --filter=ProjectContract, then run vendor/bin/pint --dirty --format agent.

Ask me before building if any of these are unclear:
  • Can the term total go above the contract amount without an extension, or should it be a hard block?
  • Should vendor retention or advance payments be handled now, or later?
  • Do contracts need a print or PDF (Browsershot), and a vendor statement?
  • Should a project contract link to an existing project or property record, or is project_name free text?
