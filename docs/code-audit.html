▶A second global cache key holding tenant data — on the POS screen
CriticalConfirmedFixed
What the code did

app/Livewire/Sale/Page.php:550

$this->categories = Cache::remember('categories_with_products', 3600, function () {
    return Category::withCount('products')
        ->having('products_count', '>', 0)
        ->when($this->category_key, fn ($q, $v) => $q->where('name', 'LIKE', '%'.$v.'%'))
        ->get()->toArray();          // Category uses BelongsToTenant
});
Why it was a problem

The same class of defect as original findings 1 and 2, which survived their cleanup. Category carries TenantScope, so the cached array is tenant-specific — but the key is global. Whichever tenant opened the POS first defined the category list for every tenant for the next hour.

There is a second bug stacked on it: $this->category_key filters the query but is not in the key, so a search result gets cached as if it were the unfiltered list. In practice getCategories() is only called from mount() where the filter is empty, which is why this never showed up as a visible search bug — but it was one edit away from doing so.

The fix
// Keyed per tenant AND per search term.
$cacheKey = TenantCache::key('categories_with_products:'.md5((string) $this->category_key));
$this->categories = Cache::remember($cacheKey, 3600, function () { /* … */ });

TenantCache::key() is used rather than tenant_cache() because the latter resolves from a fixed key registry; this value is computed, so only the key-building half applies.

▶The view own permission family was dead — and failing open
HighConfirmedFixed
What the code did

app/Livewire/LocalPurchaseOrder/Table.php:62 · PurchaseRequest/Table.php:67 · LpoPurchase/Table.php:74 · Grn/Table.php:71 · LocalPurchaseOrderPolicy.php:17, 25, 128

if (Auth::user()->can('local purchase request.view own')
    && ! Auth::user()->can('local purchase request.view')) {
    $query->ownedBy(Auth::id());
}
Why it was a problem

None of the *.view own abilities existed in config/permissions.php, and the Gate::before super-admin bypass in AppServiceProvider is commented out — so can() returned false unconditionally and the narrowing never ran. Because the guard is negative, the failure mode is fail-open: users intended to see only their own purchase orders saw everyone's instead. A missing permission that hides a button is obvious in testing; one that silently stops restricting is not.

On top of that, the group name at LocalPurchaseOrder/Table.php:62 was local purchase request — a typo for local purchase order, a group that does not exist at all.

The fix

Typo corrected, and view own added to all four groups (purchase request, local purchase order, grn, lpo-purchase) with a comment in the config explaining the negative-guard convention.

Trade-off

This one only takes effect after seeding. Note that granting view own to a role that also holds view does nothing — the narrowing is deliberately suppressed for users who hold the broader ability.

▶12 of 15 print routes had no permission check
HighConfirmedFixed
What the code did

routes/print.php

Only the day-session report and the rent-out checklist carried ->can(). The rent-out statement, utilities statement, reservation form, residential lease, payment receipt and voucher, the purchase-vendor statement and voucher, the sale invoice, and the sale-return and tailoring receipts were reachable by any authenticated user who could guess an id.

Why it was a problem

Tenant scoping still applies, so this is not cross-tenant exposure — but it is cross-role. A cashier could pull a residential lease or a vendor statement straight from the URL. The print-and-pdf skill already stated the rule ("documents a user can trigger get a .print permission"); the routes simply had not followed it.

The fix, and one design decision worth recording

Existing abilities were reused wherever one fit — sale.receipts, tailoring order.receipts, rent out lease booking.residential lease — so most roles keep working without a new grant. print was added to rent out and vendor only where nothing fit.

Rent-out documents are shared between the rent out and rent out lease agreement types, and ->can() checks a single ability — it cannot express an OR. Gating them on either group alone would have broken the other, so all rent-out print routes use one rent out.print. That is a deliberate flattening, not an oversight.

▶Mobile sale-return create had no duplicate guard
MediumConfirmedFixed
What the code did

app/Actions/V1/SaleReturn/CreateAction.php

V1/Sale/CreateAction guards against double taps and network retries with a 2-minute identical-payload window (DUPLICATE_WINDOW_MINUTES). The sale-return path — equally double-tappable on a phone, and equally prone to retry on a flaky connection — had no equivalent.

Why it was a problem

A duplicate return refunds money twice and moves stock twice. The per-line "returnable quantity" cap in buildItems() stops a second, separate return from over-returning, but it cannot see a retry of the request currently in flight — both requests read the same remaining quantity.

The fix

A matching guard on completed returns by the same user within the window, comparing an order-independent signature of the line items.

Note a schema detail that shaped the implementation: sale_returns has no sale_id column — the link to the originating sale lives on sale_return_items.sale_item_id. The first draft of this guard matched on sale_id and was wrong; it matches on the account plus the item signature instead, which is exact because the signature is built from sale_item_id values.

▶Two raw DB::table aggregates bypassing branch scope
MediumConfirmedFixed
What the code did

app/Livewire/PurchaseVendor/View.php:71 · app/Traits/BuildsCustomerReminderQuery.php:42, 54, 64

$total_purchases = DB::table('purchases')
    ->where('account_id', $this->vendor_id)
    ->whereNull('deleted_at')
    ->selectRaw('SUM(grand_total) …')->first();
Why it was a problem — and why it is only medium

Purchase and Sale both carry TenantScope and AssignedBranchScope; a raw builder drops both. This is not a cross-tenant leak in practice — the queries reach rows through account_id, and an account belongs to exactly one tenant — which is why it is rated medium rather than critical. The real defect is the branch axis: a user assigned to one branch saw vendor totals and reminder aggregates computed across every branch in the tenant.

The fix, and two behaviour changes it causes

Both now start from the model. Verified by dumping the generated SQL: the leftJoinSub sub-select carries where sales.tenant_id = ? with correctly ordered bindings — worth checking explicitly, because an Eloquent builder passed to joinSub only applies its global scopes if the framework resolves it through toSql(), which it does. Both scopes qualify their column with the table name, so the joins stay unambiguous.

Two consequences to expect: vendor totals and reminder lists now exclude branches the user is not assigned to (the point of the fix), and the totals sub-query now excludes soft-deleted sales, which the raw version silently counted.

Mechanical differences that bite when converting

  • ->pdf() returns raw bytes, not a response — there is no stream(). Wrap it: response($pdf)->header('Content-Type','application/pdf')->header('Content-Disposition', …).
  • Landscape is ->landscape(), not a paper-orientation argument.
  • showBackground() is required or Chrome prints every coloured panel white.
  • External requests are blocked, so images must be data URIs — CompanyLogoResolver::dataUri(), never tenant_cache('logo') or a /storage/… path.
  • The DomPDF-era CSS (tables, hex colours, no flex) still renders correctly in Chrome, so converted views need no restyling — but the constraints no longer bind if you redesign them.

▶21 Livewire components with write methods and no authorization guard — 6 of them unexplained
MediumConfirmedPartly fixed

This finding was overstated — the original count came from a grep that only knew one guard idiom

The “30 unguarded” figure was derived by searching for abort_unless. This codebase has a second, equally valid guard idiom: Auth::user()->cannot('x') followed by throw new Exception(...), which the component's own catch block turns into an error toast rather than a 403 page. Every file using that form was miscounted as unguarded.

The headline casualty was Grn/Table::delete(), named here as “an unguarded bulk delete”. It was never unguarded — app/Livewire/Grn/Table.php:92 has read if (Auth::user()->cannot('grn.delete')) { throw ... } the whole time. No fix was needed and none was applied.

Re-counted across all guard idioms (abort_unless, abort_if, can(), cannot(), authorize()): of 188 components with a write method, 21 have no authorization of any kind — not 30.

What the code does now

Of 188 Livewire components exposing a save/delete/store/update/destroy/submit method, 167 carry a guard in one form or the other. The remaining 21 split into two very different groups:

  • 15 carry a TODO(C7) marker recording a deliberate decision — mostly nested POS sub-components (line-item and payment-line removal inside an already-authorized create/edit flow) and settings tabs where the candidate ability was ambiguous and guessing would have denied everyone. These are defensible.
  • 6 have no marker at all, down from 10 after this pass. The four genuinely privileged ones are now guarded (see Resolution): Settings/Role/Permissions::save() and syncPermission(), Settings/Role/Page::save(), Settings/Branch/Page::save(), and Sale/Import::save().
Resolution — the four privileged ones, guarded
// Settings/Role/Permissions.php:77 and :110 — the screen that hands out every other
// permission in the system. syncPermission() re-seeds config/permissions.php, which
// is the same power, so it takes the same ability.
abort_unless(auth()->user()?->can('role.permissions'), 403);

// Settings/Role/Page.php:54 and Settings/Branch/Page.php:77 — create/edit split,
// matching the pattern already used in Property/TenantDetail/Page.
abort_unless(auth()->user()?->can($this->table_id ? 'role.edit' : 'role.create'), 403);
abort_unless(auth()->user()?->can($this->table_id ? 'branch.edit' : 'branch.create'), 403);

// Sale/Import.php:34 — bulk sale import
abort_unless(auth()->user()?->can('sale.import'), 403);

Every ability used already exists in config/permissions.php and was checked against the live grant table before the guard was written — the whole point of §05e is that a guard on an unheld ability is a dead feature, and adding five more would have repeated the mistake this report is about.

Verified: php -l and Pint clean on all four files; full Pest run shows no failure in any area they touch — and no test in the suite exercises these four components, so the guards are unverified by test, only by construction.

What is left — the 6 unmarked

None is a privilege-escalation surface; all six are settings or line-item editors reached from an already-gated route. Listed so the next pass does not have to re-derive them:

  • Sale/Feedback.php · Sale/EditItem.php · SaleReturn/EditItem.php — line-item and feedback editors inside an authorized sale flow, the same shape as the 15 marked ones
  • Settings/NotificationPreferences.php · Settings/UniqueNoCounterConfiguration.php · Accounts/ChequeConfiguration.php — settings tabs; each needs a decision on whether configuration.settings is the right ability or a narrower one should exist
Why it is a problem — with the severity stated fairly

The permissions-and-routes skill is explicit that a route-level ->can() does not protect a Livewire call, because the method is invoked on an already-open page. That is the rule being broken.

The practical exposure is narrower than it first sounds: Livewire 3 signs component snapshots, so an attacker cannot forge a call to a component they were never served. Reaching Settings/Role/Permissions still requires passing the route's role.permissions check. So this is defence in depth, not a live privilege-escalation hole — but it is exactly the layer that stops a future refactor (nesting that component somewhere less guarded) from becoming one.

Suggested approach for what remains

The four privileged components are done. For the 6 unmarked leftovers, the three settings tabs need a naming decision (reuse configuration.settings, or introduce a narrower ability) and the three sale line-item editors should almost certainly just inherit the sale flow's authorization and get a TODO(C7) marker recording that, which folds them into the batch below.

Then decide the 15 marked ones as a batch: either accept the inherited authorization and delete the markers, or introduce the sub-permissions the markers propose. Leaving them marked indefinitely is the worst of both.

And whichever ability you pick, check it is actually granted to a role first. That is the lesson of §05e sitting one section below this one: a guard on an ability nobody holds does not secure the feature, it deletes it.

▶14 CRUD actions read Auth::id() internally
LowConfirmed
What the code does now

The action layer's contract is that the actor is passed in, never read inside, so jobs, console commands and API callers can drive the same action. 14 CRUD actions break it — the app/Actions/Package/* cluster is the worst, plus Issue/Create|Update and several Item/DeleteActions.

Mockery's overload: prefix does not mock an instance — it defines the class in the PHP runtime, and the definition survives for the remainder of the process. This is the only overload: mock in the suite, and app/Actions/Sale/JournalEntryAction.php imports precisely that class. The V1 sale endpoint answers 422 and the test never reaches what it was written to check.

Mockery's own documentation requires overload mocks to run under #[RunInSeparateProcess] with preserveGlobalState: false. This test has neither.

The 2026-08-06 diagnosis was wrong. It attributed the failures to “a RefreshDatabase teardown that cannot drop tables under existing foreign keys”. The first 2026-08-09 draft of this section was also wrong, and is corrected above. It reported 119–128 failures on a re-run and concluded the suite corrupts itself across runs. The draft also blamed the 25 V1 failures on the schema-dropping tests; bisection puts them entirely on the overload: mock.

The fix — three edits, in order of payoff
  • 25 failures. Put JournalEntryActionTest's two methods in their own process — #[RunInSeparateProcess] with preserveGlobalState: false, as Mockery requires for overload:. Alternatively inject Journal\CreateAction into Purchase\JournalEntryAction so the test can pass a normal mock and the overload disappears.
  • 11 failures. StockAnalysisReportTest:89 — stop writing inventories.barcode; it is a STORED GENERATED column.
  • 7 failures, plus the latent risk. Footgun found while doing this: migrate:fresh defaults to a live database

Tests read .env.testing (DB_DATABASE=project_manager), which is correctly separate from the tenant databases. But php artisan migrate:fresh without --env=testing reads .env, which declares DB_DATABASE seven times — the last wins, so a plain migrate:fresh would drop every table in astra_daraltafseel. Every command in this section was run with --env=testing. Worth a guard, and it is the same duplicate-key hazard already recorded for APP_TIMEZONE.

Kept from 2026-08-06 — still true

A test-harness bug the tenant work exposed — found and fixed

A Laravel test case flushes its Application on teardown but leaves it memoized in Facade::$resolvedInstance. The next plain unit test that boots an Eloquent model whose traits touch a facade — Auditable reaching for Config — then died with Target class [config] does not exist, purely as a function of alphabetical file ordering. AssetDepreciationPeriodTest was the visible victim.

Fixed with a beforeEach in tests/Pest.php that detects the stale application and clears it, so facade-guarded boot code sees “no app” and skips cleanly. The related hardening is in TenantService itself: each fallback is wrapped in $app->bound(…), so resolving a tenant outside a booted framework returns null instead of throwing. Re-checked 2026-08-09: both are still in place and AssetDepreciationPeriodTest no longer fails that way.
