Areas clean

The three things to fix first

1. Tenant identity lives in a globally-shared cache key. TenantService writes the active tenant to Cache::put('current_tenant_id', …) — one key for the whole installation. Any request that cannot resolve a tenant from its subdomain falls back to reading it, so it adopts whichever tenant most recently logged in. This is the root cause that makes findings 2 and 3 dangerous rather than merely untidy.

2. Tenant-scoped data is cached under global keys for a year at boot. AppServiceProvider::boot() warms accounts_slug_id_map, branches, logo, theme_settings, payment_methods and more with no tenant in the key. The first tenant to warm the cache defines those values for every other tenant. accounts_slug_id_map feeds every journal posting in the app.

3. impersonate() has no permission check. A full account-takeover action guarded only by reaching the page.

An important qualifier on severity

Findings 1–3 are confirmed defects in the code. Whether they are currently causing harm depends on something the code cannot tell me: how many tenants this deployment actually serves. On a single-tenant installation they are latent — real, but not presently leaking. On a multi-tenant installation they are active cross-tenant data exposure. I could not determine which from the repository, so I have rated them on the multi-tenant assumption the code is written for. Confirm your deployment shape before triaging.

02Tenant & branch isolation

Measured against multi-tenancy-and-branches. The model layer is in good shape — 91 models use BelongsToTenant and 30 of 32 Rule::unique calls are correctly tenant-scoped. Every problem found here is in the caching layer sitting above it.

▶Tenant identity is stored in a globally-shared cache key
CriticalConfirmedTenancy
What the code does now

app/Services/TenantService.php:66–81 and :44, :90

public function setCurrentTenant(Tenant $tenant): void
{
    $this->currentTenant = $tenant;
    Cache::put('current_tenant_id', $tenant->id, now()->addMinutes(5));
}

public function getCurrentTenantId(): ?int
{
    if ($this->currentTenant) {
        return $this->currentTenant->id;
    }
    return Cache::get('current_tenant_id');   // ← shared by every request
}
Why it is a problem

The cache is a process-wide, cross-request store. There is one current_tenant_id value for the entire installation, not one per session.

The concrete failure: IdentifyTenant resolves the tenant from the subdomain, but when there is no subdomain it explicitly lets the request through unresolved (app/Http/Middleware/IdentifyTenant.php:26–33 — abort_if fires only for routes flagged required). Such a request reaches TenantScope, which calls getCurrentTenantId(), which falls through to the shared cache key. So: tenant B signs in on their subdomain and overwrites the key; within the next five minutes tenant A opens a page on the apex domain or localhost; every scoped query on that page silently filters to tenant B's data — and tenant A sees it.

The same fallback runs for queue workers and any API path without tenant resolution, where the value is simply whatever the last web request left behind.

The better approach

Tenant identity is request state, not shared state. Keep it in the container for the life of the request and let it die there:

// TenantService — no cross-request storage at all
public function setCurrentTenant(Tenant $tenant): void
{
    $this->currentTenant = $tenant;      // singleton is per-request; that is enough
}

public function getCurrentTenantId(): ?int
{
    return $this->currentTenant?->id;
}

Then make the absence of a tenant loud rather than silently permissive: have IdentifyTenant abort for every authenticated route, not only those flagged required. For queues, keep passing tenant_id into the job constructor and calling setCurrentTenant() in handle() — that path is already correct (app/Jobs/Product/ImportProductJob.php:38–55) and needs no cache.

Why that is better — and the trade-off

It removes an entire class of bug by construction: with no shared storage there is nothing to leak between requests. The cost is that any code path currently relying on the fallback to work without a subdomain will start returning null and, correctly, showing no data. That is the point — but it means this change needs a sweep of the no-subdomain entry points (apex domain, local development, Horizon, scheduled commands) before it ships, not a one-line edit.

If local development depends on the apex domain resolving to a tenant, set that explicitly from config (TENANT_ID in .env) rather than reintroducing a shared cache.

▶Tenant-scoped data cached under global keys for a year at boot
CriticalConfirmedTenancy
What the code does now

app/Providers/AppServiceProvider.php:57–90

Cache::remember('branches', now()->addYear(), fn () =>
    Branch::select('id', 'name')->get());          // Branch IS tenant-scoped

Cache::remember('accounts_slug_id_map', now()->addYear(), function () {
    return DB::table('accounts')              // ← raw: no TenantScope at all
        ->where('is_locked', 1)
        ->pluck('id', 'slug')->toArray();   // ← slug is the KEY: last tenant wins
});

Cache::remember('logo', …); Cache::remember('theme_settings', …);
Cache::remember('payment_methods', …); Cache::remember('barcode_prefix', …); // …and more
Why it is a problem

Three compounding defects in one block:

  • The cache keys carry no tenant. Cache::remember runs its closure only on a miss, so whichever tenant's request warms the cache first defines these values for every tenant — for a year.
  • accounts_slug_id_map is built from a raw query, so even the read that populates it ignores TenantScope. Because it plucks keyed by slug, two tenants each owning a locked sale account collapse into one entry and the higher id silently wins.
  • Invalidation makes it worse, not better. The settings screens do call Cache::forget('logo'), forget('theme_settings') and friends (app/Livewire/Settings/CompanyProfile.php:71–84, ThemeSettings.php:74). Because the key is global, tenant A saving their logo clears the shared entry and republishes A's logo to everyone. The value flaps to whoever saved last.

The blast radius of the account map is the whole general ledger: Cache::get('accounts_slug_id_map') is read by at least ten JournalEntryActions (Sale, Purchase, SaleReturn, PurchaseReturn, Tailoring, SupplyRequest, InventoryTransfer…) plus the tax reports. If it holds another tenant's ids, every posting debits and credits accounts belonging to a different company, and the books are wrong in a way no screen will flag.

The better approach

Key the cache by tenant and resolve it lazily, not at boot:

// A small accessor, called where the map is used — not in a service provider
public static function slugIdMap(): array
{
    $tenantId = app(TenantService::class)->getCurrentTenantId();

    if (! $tenantId) {
        throw new RuntimeException('No tenant resolved; refusing to build the account map.');
    }

    return Cache::remember("accounts_slug_id_map:{$tenantId}", now()->addDay(), fn () =>
        Account::query()                 // model, so TenantScope applies as a second guard
            ->where('is_locked', 1)
            ->pluck('id', 'slug')
            ->toArray());
}

Apply the same :{$tenantId} suffix to branches, logo, theme_settings, payment_methods, barcode_type, barcode_prefix, sale_type — and update the matching Cache::forget() calls in the settings components to forget the tenant-suffixed key.

Refusing to build the map without a tenant is deliberate: a missing map surfaces as a loud error at posting time instead of silently posting to null account ids.

Why that is better — and the trade-off

Per-tenant keys are the minimum correct thing; moving the warm-up out of AppServiceProvider::boot() is the part that actually fixes it. Boot runs before routing, so no tenant is reliably known yet — any tenant-dependent value computed there is a guess. Resolving lazily at the call site guarantees a tenant is in scope.

Trade-off: you lose the "everything is warm after the first request" property and take a cache miss per tenant per key. That is a few queries per tenant per day against a year of silently wrong ledger postings — not a close call. Shortening the TTL from a year to a day is a separate small win: a stale-cache bug then self-heals overnight instead of persisting until someone runs cache:clear.

▶Ledger accounts resolved by raw query on display name — 10 sites
CriticalConfirmedAccounting
What the code does now

4 listeners, 4 payment actions, 3 Livewire components — identical line

$discount_id = DB::table('accounts')->where('name', 'Discount')->value('id');

Confirmed at: app/Listeners/SaleUpdateEventListener.php:18, PurchaseUpdateEventListener.php:18, SaleReturnUpdateEventListener.php:18, PurchaseReturnUpdateEventListener.php:18, app/Actions/Sale/ReceiptAction.php:34, app/Actions/SaleReturn/PaymentAction.php:34, app/Actions/Purchase/PaymentAction.php:37, app/Actions/PurchaseReturn/PaymentAction.php:37, app/Livewire/Sale/CustomerReceipt.php:46–47, app/Livewire/Purchase/VendorPayment.php:48–49, app/Livewire/SaleReturn/CustomerPayment.php:47.

Why it is a problem

Two independent defects on one line:

  • DB::table() bypasses TenantScope. It returns the first Discount row in the whole table regardless of owner — so tenant B's discounts post to tenant A's discount account.
  • Matching on name is fragile. The accounts table has a slug column and an is_locked flag precisely so system accounts can be identified stably. Any tenant who renames "Discount" to "Discount Allowed" in their chart of accounts gets null — which is then written into account_id on a journal entry with no error.

Note lines 46–47 of CustomerReceipt.php and 48–49 of VendorPayment.php are the same statement twice in a row, assigning to the same key — a copy-paste artefact that doubles the query cost and signals this line was propagated by duplication rather than written.

The better approach

Use the same slug map the rest of the accounting layer already uses — fixed per finding 2 so it is tenant-keyed:

$accounts = Account::slugIdMap();
$discountAccountId = $accounts['discount'] ?? throw new Exception(
    'The Discount account is not configured for this tenant.'
);

That is already the established pattern — app/Actions/Sale/JournalEntryAction.php:29 and nine sibling actions resolve every account this way. These ten sites are the stragglers.

Why that is better — and the trade-off

It restores tenant isolation, makes the lookup rename-proof, and collapses eleven duplicated lines into the one accessor that already exists. Throwing on a missing account converts a silent mis-posting into a visible configuration error, which is the correct trade for accounting code.

The one genuine cost: tenants whose chart of accounts predates the slug column may have a Discount account with a null slug, and would hit the new exception. Backfill slugs for locked accounts before deploying this, and keep the exception rather than a silent ?? null fallback — a loud failure at configuration time beats a quiet one in the ledger.

Clean in this area

Validation uniqueness: 30 of 32 Rule::unique declarations correctly scope by tenant_id. The two that do not — Country and Tenant — are genuinely global tables and are right as written. Two more (PackageItem.php:22, AppointmentItem.php:37) use the Rule::unique('table_name') string form, which bypasses the model's global scope, but both narrow by a parent id that is itself tenant-scoped, so they are transitively safe. Worth tidying for consistency, not a defect.

Queued jobs: the tenant-context pattern is correctly implemented — ImportProductJob sets setCurrentTenant() from a constructor-passed id and clears it in a finally. This is the pattern the other findings should be measured against.

03Authorization

Measured against permissions-and-routes. Coverage is much better than the raw file counts suggest: 193 of 355 Livewire components carry an explicit check, and 82 of the 84 components with a delete() method guard it. The gaps are specific and already known to the team.

▶User impersonation has no permission check
HighConfirmedAuthz
What the code does now

app/Livewire/User/View.php:86–103

public function impersonate()
{
    // TODO(C7): unmapped (candidate: 'user.edit') — no impersonate permission in
    // config/permissions.php; account-takeover action needs a dedicated permission.
    try {
        $targetUser = User::find($this->table_id);
        …
        Auth::login($targetUser);
        session(['branch_id' => $targetUser->default_branch_id]);
        request()->session()->regenerate();

        return $this->redirect(route('dashboard'));
Why it is a problem

This is a complete, unguarded account takeover. Anyone who can reach the user-view screen and trigger the Livewire method becomes any other user in their tenant — including an administrator — with a regenerated session and no audit trail distinguishing the impersonation from a genuine login. The TenantScope on User does confine the blast radius to the current tenant, which is the only thing keeping this out of the critical band.

Livewire methods are directly addressable. A route-level guard on the page would not be sufficient here even if one existed, and none of the user routes in routes/settings.php matched a can() check for this screen.

The better approach
// config/permissions.php
'user' => ['create', 'view', 'edit', 'delete', 'impersonate'],

// app/Livewire/User/View.php
public function impersonate()
{
    abort_unless(auth()->user()?->can('user.impersonate'), 403);
    abort_if($this->table_id === Auth::id(), 400);
    …
}

Then seed it (php artisan db:seed --class=PermissionSeeder) and grant it to the administrator role only. Log the impersonation start and end against the impersonator's id — the code already stores session(['impersonator_id' => Auth::id()]), so the information is there and simply is not recorded.

Why that is better — and the trade-off

A dedicated permission rather than reusing user.edit matters here: editing a user and becoming a user are different powers, and support staff routinely need the first without the second. There is no real trade-off — the cost is one config line and one guard. The only judgement call is whether to add the audit log now or later; given this is the single highest-privilege action in the application, now.

▶20 actions marked as having no mapped permission
MediumConfirmedAuthz
What the code does now

A prior pass left 20 TODO(C7): unmapped markers where an action has no corresponding entry in config/permissions.php. They cluster into three groups:

  • Missing export actions — rent out utility, rent out cheque, rent out service, and property lead all have bulk Excel exports with no .export permission (RentOut/UtilityPaymentTable.php:99, ChequeManagementTable.php:83, ServicePaymentTable.php:175, Property/PropertyLead/Table.php:128).
  • Commented-out groups — tenant detail (TenantDetail/Table.php:35, Page.php:74).
  • Genuinely unmapped modules — trading, working-day settings, one supply-request image delete.
Why it is a problem

Unmapped exports are the material ones: a bulk Excel export of every lease cheque or every property lead is a data-exfiltration surface available to any role that can view the list. Data export is consistently a distinct permission everywhere else in this codebase (account.export, customer.export, sale.export…), so these are inconsistencies rather than deliberate design.

The better approach

Add the four missing export actions to their existing permission groups in config/permissions.php, seed, and replace each TODO with the guard. That clears 5 of 20 markers for near-zero effort and closes the actual data-egress gap. The rest are decisions about module scope, not oversights — resolve them by deciding whether each module ships, and delete the markers you consciously accept.

Why that is better — and the trade-off

Adding a permission to an existing group is safe and additive. The one operational catch: newly seeded permissions are granted to nobody by default, so an export button that worked yesterday will 403 until the permission is assigned to the relevant roles. Assign roles in the same deployment, or users will report it as a regression.

04Action & Livewire layers

Measured against action-layer and livewire-components. The core discipline holds well — every one of the 116 Livewire files that opens a transaction also has a matching rollback. Two systemic inconsistencies stand out, and one of them means the skill is wrong.

▶Two competing transaction conventions — the skill overstates the rule
MediumConfirmedSkill defect
What the code does now

The action-layer skill states flatly that "actions do not open transactions; the caller does." 33 action classes disagree, and they are not strays — they are the newer modules, and they are internally consistent:

// app/Actions/RentOut/DeleteAction.php:23 — and 32 others
DB::transaction(function () use ($model) { … });

They cluster as: all 5 V1 API actions, all 7 Maintenance/Complaint actions, 4 StockCheck actions, 2 Asset actions, 7 RentOut sub-actions, plus Issue, Tailoring and EmployeeCommission. Meanwhile the original core — Sale, Purchase, Journal, SaleReturn — has no transaction and relies on the caller, exactly as the skill describes.

Why it is a problem

Mostly it is a documentation defect: the skill asserts a rule the codebase does not follow, and an agent applying it literally would "fix" 33 correct files. The V1 actions in particular are right to self-transact — they are called from controllers, and there is no Livewire component to own the boundary.

There is one real runtime consequence. app/Livewire/RentOut/Table.php:150 opens a transaction and then calls RentOut\DeleteAction, which opens its own (DeleteAction.php:23). Laravel handles the nesting via savepoints, so this is not corrupting data today — but a reader cannot tell at a glance which boundary owns a rollback, and the inner block silently becomes a savepoint rather than the transaction its author appears to have written.

The better approach

State the actual rule, which the code already follows once you look at who the caller is:

CallerWho owns the transactionWhy
Livewire componentThe componentOne user gesture may drive several actions; only the component knows the full unit of work
V1 API controllerThe actionOne request = one action; a controller-level boundary would be pure ceremony
Queued job / commandThe actionSame reason; no interactive caller exists
Another actionNeither — inheritNesting creates savepoints; let the outermost boundary win

Then fix the one genuine overlap by removing DB::transaction() from RentOut\DeleteAction, since its only callers (RentOut/Table.php, BookingTable.php) both already wrap it.

Why that is better — and the trade-off

Codifying the caller-based rule beats forcing 33 files onto the older convention: it matches what the code does, keeps the API and queue paths safe by default, and gives a clear test for new code ("who calls this?"). The trade-off is that "it depends on the caller" is a weaker rule than "never" — it requires the author to check. That is the honest cost of a codebase with two legitimate entry points, and the alternative (mechanically stripping transactions from the V1 actions) would introduce real bugs to satisfy a doc.

Action required on the skill itself, not just the code — see §07.

▶Success toast dispatched before the commit — ~59 files
MediumConfirmedLivewire
What the code does now

app/Livewire/RentOut/Table.php:160–161 — representative of ~59 files

    $this->dispatch('success', ['message' => 'Successfully Deleted '.count($this->selected).' items']);
    DB::commit();

Sampled by grep across app/Livewire for a dispatch('success') within three lines before a DB::commit(); roughly 59 files match, including Account/Customer/Table.php:55, Account/Expense/Page.php:120, InventoryTransfer/Page.php:214, Maintenance/Table.php:72.

Why it is a problem

The user is told the operation succeeded before it is durable. If DB::commit() throws — deadlock, lock-wait timeout, connection loss, a deferred constraint — the catch block fires DB::rollback() and dispatches an error toast, so the user sees a success message followed by a failure message for the same action, with the data unchanged. Under a deadlock on a busy branch this is not hypothetical.

Severity is Medium rather than High because the data outcome is still correct — the rollback works. The defect is that the UI lies about it, which in an ERP means someone believes a payment or a deletion landed when it did not.

The better approach
    DB::commit();
    $this->dispatch('success', ['message' => 'Successfully Deleted '.count($this->selected).' items']);

Nothing more — move the line. This matches app/Livewire/Sale/Page.php:1061–1068, which already commits first and only then dispatches the toast, the print event and the WhatsApp send. That file is the correct reference for the whole codebase.

Why that is better — and the trade-off

Every post-commit side effect — toast, print dispatch, notification, external send — belongs after the commit for the same reason: it is externally visible and cannot be rolled back. There is no downside; the ordering is free.

The only caution is mechanical: this is a ~59-file sweep of near-identical two-line swaps, which is exactly the kind of change that is easy to apply blindly and get subtly wrong where a $this->mount() or resetPage() call sits between the two lines. Do it in one reviewed pass per module rather than a regex across the tree.

Why it is a problem

The print-and-pdf skill records the rule the team already learned the hard way: DomPDF renders Arabic unshaped and reversed, which is why the rent-out checklist was migrated to Browsershot. But these six documents remained on DomPDF, and every one of them prints $rentOut->customer?->name and $companyName — a tenant-editable company name and a customer name, in a UAE real-estate product where Arabic names are ordinary.

The failure is quiet: nothing errors. A tenant with Arabic-named customers gets statements and vouchers with mangled, right-to-left-reversed, disconnected glyphs — on documents they hand to customers and vendors. Rated High rather than Critical only because the numbers, which are what the document is actually for, still render correctly.

The better approach

use UsesBrowsershot;

$companyLogo = CompanyLogoResolver::dataUri();   // external URLs are blocked; embed it
$html = view('print.rentout.statement', $data + compact('companyLogo'))->render();

return $this->makeBrowsershot($html)
    ->format('A4')->margins(10, 10, 10, 10)
    ->showBackground()
    ->pdf();

The views need a pass too: DomPDF views are written table-first with hex colours, which Chrome renders fine, but any <img src="/storage/…"> must become a data URI and showBackground() is required or every coloured panel prints white.

Why that is better — and the trade-off

This is the one place in the report where I would not recommend converting everything. The trade-off is real and cuts both ways:

DomPDFBrowsershot
Arabic / RTLBroken — unshaped, reversedCorrect
SpeedFast, in-processSpawns Chrome — hundreds of ms, more memory
Deploy dependencyNoneNeeds node + Chrome on every server
CSS~CSS 2.1; tables onlyModern — flex, grid, var(), color-mix()
AssetsLocal paths workMust be inlined as data URIs
Best forHigh-volume Latin-only documentsAnything with user-authored or Arabic text

Recommendation: convert the four rent-out documents, which are customer-facing and carry customer names. The two purchase-vendor documents are a weaker case — vendor names are more often Latin — but they print $companyName from tenant settings too, so convert them as well unless the Chrome dependency is a problem on the print server. If it is, the honest middle option is to keep DomPDF and embed a shaping-capable Arabic font, but that only fixes glyph shaping, not bidirectional ordering, and will still look wrong in mixed Arabic/Latin lines. Browsershot is the right answer; the cost is operational, not architectural.
