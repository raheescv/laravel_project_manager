The headline: the skills are unusually accurate on structure

Every count asserted across the twelve skills was checked and every one matches exactly — 383 actions, 355 Livewire components, 60 exports, 13 imports, 38 jobs, 134 models with 91 on BelongsToTenant, 32 self-transacting actions (21 closure + 11 manual), 28 shared select components. Every file path and helper they name exists. That is rare, and it means the skills can be trusted as a map. One count in an earlier draft of this report was wrong where the skill was right — recorded in §04d, because how it went wrong applies to every other figure here.

The failures are all in prose that went stale as the code moved underneath it — not in invented detail. Three skills describe an architecture the codebase has since left behind.

The one that would actively cause damage

blade-ui-conventions says Vite "only build[s] the POS, React, and Vue bundles — do not reach for them when working on an ordinary admin screen." That is wrong in a way an agent will act on: the Purchase page and the General Voucher / Journal Entry modal are Vue apps built by Vite and mounted inside Livewire Blade views. An agent following this skill would hand-write a Blade+Alpine replacement for a screen that already has a Vue implementation, and never find the real one.

02The hook

One hook is configured, in .claude/settings.local.json. It is correct. The notes below are refinements, not defects.

// PostToolUse · matcher: Write|Edit · timeout 30s
f=$(cat | jq -r '.tool_input.file_path // .tool_response.filePath') \
  && case "$f" in *.php) ./vendor/bin/pint "$f" ;; esac || true
CheckResult
jq availableYes /usr/bin/jq
pint runsYes Pint 1.27.1, preset: laravel with three rule overrides
Does *.php also catch *.blade.php, and would Pint mangle it?Safe The glob does match, but Pint is a no-op on Blade — PHP-CS-Fixer's finder skips templates. Tested on a deliberately messy Blade file with an unformatted @php block: reported pass, byte-identical output.
Failure handlingCorrect || true means a Pint failure never blocks the edit — right choice for a formatter
Path resolutionRefinement ./vendor/bin/pint is relative to the cwd. It silently no-ops if the harness is started anywhere but the repo root — relevant given this project uses git worktrees. "$CLAUDE_PROJECT_DIR/vendor/bin/pint" is exact.
CoverageGap PHP only. Nothing equivalent guards the Flutter packages, where the project rule is stricter (see §05).

Known behaviour worth designing around, not fixing

Pint's laravel preset removes unused use imports. When an import is added in one edit and its usage in the next, the hook fires in between and strips the import — leaving code that passes php -l but fails at runtime on an unresolved class. This happened three times during this session's work and was caught each time by re-checking imports afterwards.

The mitigation is ordering, not configuration: introduce the usage first and add the use statement last, or make both in a single edit. Worth keeping in the memory file it is already recorded in.

04Where the skills were wrong

Ordered by how much damage following the skill would do.

▶blade-ui-conventions — misstates what Vite builds
HighConfirmedOpen
What the skill says

"Vite/Tailwind exist in the repo but only build the POS, React, and Vue bundles — do not reach for them when working on an ordinary admin screen."

What the code does

vite.config.js:8–17

input: [
    'resources/css/app.css',
    'resources/js/app.js',
    'resources/js/inventory-stock-adjustment.js',
    'resources/js/stock-check.js',
    'resources/js/general-voucher-modal.js',   // ← Vue, mounted in a Livewire Blade view
    'resources/js/journal-entries-modal.js',
    'resources/js/purchase-page.js',            // ← Vue, the Purchase screen itself
    'resources/js/barcode-template-config.js'
]

purchase-page.js mounts PurchasePage.vue into resources/views/livewire/purchase/page.blade.php. general-voucher-modal.js mounts GeneralVoucherPage.vue into the account views. These are ordinary admin screens by any definition.

Why it matters

This is the one skill error that would cause an agent to write the wrong thing rather than merely describe the wrong thing. Asked to change the Purchase page or the Journal Entry modal, an agent following this skill would look only at Blade and Alpine, conclude the screen needs building, and produce a parallel implementation — leaving two Purchase pages, one of them dead.

Suggested wording

Replace the exclusion with the actual split: Blade + Bootstrap + Livewire is the default for admin screens, except the handful listed in vite.config.js, which are Vue islands mounted inside a Livewire view. Check vite.config.js before assuming a screen is pure Blade. Left unfixed here because the right replacement wording is a judgement about where the project intends the Vue/Blade boundary to sit.

▶imports-exports-and-jobs — the FromQuery rule is too absolute
MediumConfirmedOpen
What the skill says

"FromQuery (not FromCollection) so large exports stream."

What the code does

36 exports use FromQuery; 14 use FromCollection. Read individually, all 14 are aggregate reports whose rows are computed rather than selected: trial balance, balance sheet, profit & loss, P&L statement, customer and vendor aging, tax report, monthly and day-wise sale summaries, productivity and employee reports, product-wise inventory log, rent-out service charge.

Verdict: the code is right and the skill is wrong

There is no query that returns a trial balance row — it is assembled in PHP from ledger aggregates. FromQuery is not applicable, and forcing it would mean inventing a query that does not exist. An agent applying the rule literally would "fix" 14 correct exports into worse ones.

Suggested wording

"FromQuery for anything that maps onto a table query, so large exports stream. FromCollection is correct — and used by 14 exports — where rows are computed rather than selected: trial balance, P&L, aging and period summaries. If you can write the query, use FromQuery."

▶imports-exports-and-jobs — the retry warning points at the wrong risk
MediumConfirmedOpen
What the skill says

Sets $tries = 1 and $timeout = 3600 as the pattern, and warns: "keep below the queue retry_after (DB_QUEUE_RETRY_AFTER) or a running job is re-picked … the classic double-import."

What the deployment actually does
SettingValueEffect
DB_QUEUE_RETRY_AFTER (.env)3700Deliberately raised from the 90 default
Horizon supervisor-1.tries1Retries are already off globally, for every job
Horizon supervisor-1.timeout60Any job without its own $timeout is killed at 60 seconds
Jobs setting $tries = 12 of 12 importsRedundant with the Horizon setting, but harmless

Because Horizon sets tries = 1 for the whole supervisor, the double-import the skill warns about cannot happen regardless of what individual jobs declare. The skill's emphasis is misplaced.

The risk that is real instead

A job-level $timeout overrides the worker's. Ten of the twelve import jobs declare none, so they inherit Horizon's 60 seconds — a large customer or property import is killed mid-file, having already written part of it. The two that declare $timeout = 3600 (ImportProductJob, MigrateSalesChunkJob) are the only ones that can finish a big file. The number to check is not retry_after; it is Horizon's timeout.

Suggested wording

"Horizon's supervisor-1 already sets tries = 1, so retries are off globally — a per-job $tries is belt-and-braces. What you must set is $timeout: the supervisor's default is 60 seconds, and any import that can exceed it will be killed part-written. Set it explicitly and keep it under DB_QUEUE_RETRY_AFTER (currently 3700)."

▶action-layer — one stale line reference, and an audit error worth recording
LowConfirmedFixed
The real defect: a line reference this session broke

The canonical Livewire shape was cited at app/Livewire/Sale/Page.php:1039. It is now at :1044 — the tenant-cache fix made earlier in this session added five lines above it. Self-inflicted staleness, and a clean illustration of why line-number citations decay.

The transaction counts are correct — an earlier draft of this audit was not

The skill states 32 self-transacting classes = 21 closure + 11 manual. A first pass of this audit reported that as wrong (claiming 33 = 21 + 12) and "corrected" the skill. The skill was right.

The error came from counting with grep -rl, which matches inside comments. app/Actions/RentOut/DeleteAction.php:23 contains:

// BookingTable.php both wrap this call in DB::beginTransaction());

— a comment explaining that its caller owns the boundary. Grep counted it as a self-transacting action; it is the opposite. Re-counted with PHP's own tokenizer, discarding T_COMMENT/T_DOC_COMMENT, the split is exactly 21 + 11 = 32, with no file using both idioms.

Why this is worth a paragraph rather than a quiet fix

Every count in this report and its companion was produced by grep or a grep-like script. This is the one case where a claim was checked against a second, stricter method — and the stricter method disagreed. Counts of a pattern (DB::beginTransaction, Auth::id(), abort_unless) are inflated wherever that pattern appears in a comment discussing it, and comments discussing a convention cluster precisely in the files that deliberately depart from it.

Treat every "N files do X" figure in these reports as an upper bound unless it says otherwise. The figures re-derived by tokenizer or by reading are marked as such.

Line references across the skill set

All three remaining citations are correct: helper.php:517, Sale/Page.php:1044, app.blade.php:272. Useful enough to keep, but they need re-checking whenever the file they point into is edited.

05Code defects this audit surfaced

Reading imports-exports-and-jobs against the code turned up two defects that neither previous pass covered. Both are in queued imports — the area the skill itself calls "the non-obvious hazard".

▶ImportSaleJob never establishes tenant context
HighConfirmedOpen
What the code does now

app/Jobs/Sale/ImportSaleJob.php

public function __construct(
    protected $user_id, protected $filePath, protected $branchId = null
) {}   // ← no $tenantId

public function handle()
{
    $file = storage_path('app/public/'.$this->filePath);
    // … no setCurrentTenant() anywhere in the class
    Excel::import(new SaleImport($this->user_id, $totalRows, $this->branchId), $file);
}

Its siblings do it correctly — ImportAccountsJob and ImportPropertyJob both take a tenant id and call setCurrentTenant().

Why it is a problem

TenantService resolves in this order: subdomain or tenant header → authenticated user → the TENANT_ID config fallback. A queued job has no request and no authenticated user, so a sale import falls all the way through to TENANT_ID.

The failure is silent and directional: every imported sale lands in whichever tenant that env var names, regardless of who uploaded the spreadsheet. On a single-tenant install it happens to be right. On a multi-tenant install, tenant B uploading a sales file writes rows into tenant A — and because BelongsToTenant auto-fills on create, nothing errors.

The fix

Follow the sibling jobs: take $tenantId in the constructor, call setCurrentTenant() at the top of handle(), and clear it in a finally so a long-lived worker does not carry the tenant into the next job it picks up. Not applied here because it needs a matching change at the dispatch site, which is outside what was agreed for this pass.

▶Ten of twelve import jobs will be killed at 60 seconds
MediumConfirmedOpen
What the code does now

Only ImportProductJob and MigrateSalesChunkJob declare $timeout = 3600. The other ten — accounts, general voucher, checklist items, property, sale, category, dropbox product images, stock-check items, rent-out, services — declare none and inherit Horizon supervisor-1's timeout: 60.

Why it is a problem

The skill's own chunked-import pattern exists precisely because these files are large. A 5,000-row property import that takes longer than a minute is terminated by the worker part-written; because tries = 1, it is not retried, so the user sees a job that simply stopped with half the rows loaded and no error surfaced to them.

Rated medium rather than high because it fails closed — partial data and a visible stall, not silent corruption — and because whether 60 seconds is actually exceeded depends on file sizes this audit cannot see.

The fix

Declare $timeout explicitly on every import job, sized to the largest file the module realistically accepts and kept below DB_QUEUE_RETRY_AFTER (3700). Copy the ImportProductJob shape.
